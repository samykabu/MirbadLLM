Runtime

Runtime

What it is
The engine that serves the model, from the runtimes this node reports.
Why it matters
The settings on this page belong to the runtime. A node lists the runtimes it can run in its capabilities.
Example
vLLM for most models on a Linux node.

Keep serving during jobs

What it is
Keep answering requests for this model while a benchmark or tuning job runs on another model on the same node.
Why it matters
By default a job pauses every model on its node, so its measurements are not disturbed by other traffic. Keeping this one serving trades some measurement noise for availability; the runs then record that noise was possible. The model under test itself always pauses. It takes effect once node-scoped maintenance is switched on.
Example
On for an embedding model that other services call all day; off for a chat model you benchmark often.

Identity

How the controller and API clients refer to this model.

Id

What it is
A stable slug for this model: lowercase letters, digits and hyphens, starting with a letter or digit, max 40 characters.
Why it matters
The controller names the container ss-{id} and uses {id} as the registry key. It can't be changed after creation without deleting and re-adding the model.
Example
qwen-coder-7b, whose container is then named ss-qwen-coder-7b.

Served name

What it is
The name clients put in the OpenAI "model" field of a chat request.
Why it matters
The router matches incoming requests to an upstream by this exact name (case-insensitive), and it is passed to the server so /v1/models advertises it too. Two models can't share one.
Example
Qwen-Coder-7B, the name VS Code or Cline then shows in its model picker.

Model path

What it is
The checkpoint's folder name, relative to the models root (bound read-only at /models in the container).
Why it matters
The runtime loads this folder. It must be the exact folder name containing config.json and the *.safetensors weight files.
Example
Ornith-1.5-9B-uncensored, or Ornith-1.5-9B-NVFP4 for the pre-quantized variant.
Tags

Tags

What it is
Labels for finding the model: built-in ones (Chat, Embedding, Vision, Tool calling, …) and your own, lowercase letters, digits and hyphens, up to 24 characters, at most 12 per model.
Why it matters
The Dashboard and the Models page filter by tag (a model must have every selected tag), and the admin API accepts ?tag=…. Tags are not launch arguments: changing them never restarts the model. "Suggested" marks the tags the parsers, extra args and the checkpoint's config.json point to; they are only applied when you pick them.
Example
An embedding model started with --runner pooling gets Embedding suggested; Ornith-9B with the qwen3 parsers gets Chat, Tool calling and Reasoning.
1 of 12. Changing tags never needs a restart.

Source

Where the checkpoint comes from, so a restore from a backup can download it again.

Repo id

What it is
The Hugging Face repo this model's checkpoint folder (Model path) was downloaded from.
Why it matters
A restore from a backup downloads every missing checkpoint again from here. Without it, a restored model has no weights until you copy the folder back by hand. Set automatically when the model is added through "Download from Hugging Face".
Example
ornith-ai/Ornith-1.5-9B for a model whose Model path is Ornith-1.5-9B.

Revision

What it is
Branch, tag or commit SHA the restore downloads. Blank means the repo's default branch.
Why it matters
Pinning a commit makes a restore fetch exactly the files the model ran with, even if the repo changes later.
Example
Blank for most repos; a 40-character commit SHA to pin a known-good snapshot.

Allow patterns

What it is
Glob patterns of the files the restore fetches (comma-separated). Blank uses the download defaults.
Why it matters
Keeps a restore from pulling files the model never used, such as other GGUF quantizations in the same repo.
Example
Blank for a safetensors repo; "Model-Q4_K_M.gguf, *.json" for one GGUF variant.

Memory and context

The budget is checked against free memory before the model starts, so it must cover weights, KV cache and activations.

Memory budget (GiB)

What it is
Unified memory reserved for this model's container: weights + runtime overhead + KV cache, in GiB.
Why it matters
Converted to --gpu-memory-utilization (this value / total unified memory) since the DGX Spark's CPU and GPU share one memory pool. Starting a model that would push used+reserve past what's available is refused unless you force it.
Example
36 GiB of the box's 121.7 GiB total -> --gpu-memory-utilization 0.3000 (4 decimal places). The suggested value shown when you pick a folder uses: weights GiB + 7 GiB runtime overhead (measured on this box) + KV cache for up to 131072 tokens at fp8, rounded up to a whole GiB. The budget must hold at least one request of Max model len tokens, or vLLM refuses to start: 262,144 tokens on the 9B model needs about 20 GiB.

Max model len

What it is
Maximum context length (prompt + generation) in tokens that this model instance will accept.
Why it matters
Bounds how much KV cache memory a single request can use; requests longer than this are rejected by vLLM rather than silently truncated. Presets are filtered to the checkpoint's own max_position_embeddings.
Example
262144 (256K) is the checkpoint's own limit and what Phase 0 tested up to (137 s cold prefill, 1.2 s with a prefix-cache hit).

Max num seqs

What it is
Maximum number of requests vLLM will batch and run concurrently.
Why it matters
Raising it increases throughput (more requests share the same forward pass) up to a point, but each concurrent sequence needs its own slice of the KV cache budget.
Example
16 was the concurrency Phase 0 measured aggregate throughput at: 326 tok/s (FP8) and 485 tok/s (NVFP4) with 256-token outputs.

Max batched tokens

What it is
vLLM --max-num-batched-tokens: how many tokens one scheduler step may process, which is also the chunk size for long prompts (chunked prefill).
Why it matters
A larger budget prefills long prompts in fewer, bigger steps (faster time to first token) but makes decode steps of other requests wait longer behind them; a smaller one keeps streaming smooth under load. Default lets vLLM pick for this model.
Example
Tuning tries 2,048, 8,192 and 16,384 on this box and keeps whichever scores best for the chosen goal.

KV cache dtype

What it is
Storage format for the attention KV cache: auto (same dtype as the weights) or fp8.
Why it matters
The KV cache, not the weights, is usually what limits how much context you can serve concurrently. fp8 halves that memory, roughly doubling how many tokens of context fit in the same budget.
Example
fp8 on every Phase 0 model — it's what turns a 36 GiB budget into ~1.45M tokens of KV cache for the 9B model.
Halves KV cache memory vs. auto.

Quantization

What it is
Online quantization vLLM applies while loading full-precision weights. "None" means the checkpoint is already quantized (compressed-tensors/ModelOpt NVFP4, FP8, etc.) and needs no conversion at load time.
Why it matters
Quantizing at load time trades a little extra load time and (usually) a little quality for roughly half the weight memory of BF16 — the difference between 18 GiB and ~9 GiB of weights for this 9B model.
Example
fp8 for the uncensored BF16 checkpoint (Phase 0: 23.4 -> 326.0 tok/s from N=1 to N=16). Pre-quantized NVFP4 checkpoints use "None" here — they're already compressed on disk.
Checkpoint already quantized, or run at full precision.

Parsers

Turn the model's raw output into OpenAI tool calls and reasoning content. They must match the model family.

Tool call parser

What it is
Which vLLM parser extracts OpenAI-style tool calls from this model's raw output.
Why it matters
Different model families emit tool calls in different textual formats (JSON blocks, XML tags, Python-call syntax); the parser has to match the family or tool calls won't be recognized at all.
Example
qwen3_coder — Qwen3.5/Qwen3-Next/Qwen3 models emit XML-style <tool_call><function=...> calls, which is what this parser expects. Phase 0 confirmed it works even with VS Code's schema-without-properties case.

Reasoning parser

What it is
Which vLLM parser separates this model's "thinking" text from its final answer.
Why it matters
Reasoning models wrap chain-of-thought in a family-specific delimiter; the right parser strips it into a separate reasoning field instead of leaving it mixed into the visible reply.
Example
qwen3 for every Qwen3/Qwen3.5 model on this box. Leave both parsers unset for a model whose family isn't in the list.

Performance

Compilation and decoding options. The defaults are the settings measured on this box.

CUDA graph mode

What it is
vLLM's CUDA graph capture mode: how much of the forward pass gets captured as a replayable graph.
Why it matters
Graphs cut per-step launch overhead, but on this GB10 board FULL graphs crash when combined with MTP (CUBLAS_STATUS_INTERNAL_ERROR / illegal instruction on sm121); PIECEWISE is what actually worked in Phase 0.
Example
PIECEWISE — required whenever speculative decoding (MTP) is enabled on this box. Leave blank (vLLM default) for a plain model.

Prefix caching

What it is
Reuses the KV cache of a previously seen prompt prefix instead of recomputing it. On passes --enable-prefix-caching, Off passes --no-enable-prefix-caching, vLLM default passes neither.
Why it matters
Huge win for repeated system prompts or long shared context (agent loops, RAG). Phase 0 measured a 242K-token prompt drop from 137 s cold prefill to 1.2 s on a prefix-cache hit.
Example
Enabled for every Phase 0 model; there's essentially no reason to turn it off on this workload.

Async scheduling

What it is
vLLM's asynchronous scheduler: On passes --async-scheduling, Off --no-async-scheduling, vLLM default neither.
Why it matters
Overlaps scheduling with the GPU step, which NVIDIA's DGX Spark recipes use; whether it helps depends on the model.
Example
On for qwen36-35b-a3b-nvfp4 (it used to be a raw --async-scheduling extra arg).

Other compilation-config keys (JSON)

What it is
Any other --compilation-config key besides the CUDA graph mode, as a JSON object; merged with it into one argument.
Why it matters
Keeps advanced compilation settings in the definition instead of a raw -cc/--compilation-config extra arg that would override the graph mode.
Example
Leave empty unless a recipe asks for e.g. {"pass_config":{"enable_fusion":true}}.

Speculative decoding

What it is
Speculative decoding: a cheap draft step proposes several tokens, the model verifies them in one pass.
Why it matters
Can raise single-stream throughput noticeably when the draft's guesses are often right, at the cost of extra GPU work per verification step that doesn't pay off when the draft is wrong a lot.
Example
MTP on the official NVFP4 checkpoint: 48.1 tok/s at N=1 vs 41.0 without it (matching acceptance ~1.76 on story prompts). The uncensored checkpoint has no MTP weights, so speculative decoding isn't available for it.

Container

The image the model runs in, raw vLLM arguments, and whether it starts with the controller.

Image override

What it is
The Docker image to run this model's container from. Blank uses the deployment's default vLLM image.
Why it matters
Different images can carry different vLLM builds/model support (the nvcr vllm:26.01 image, for example, lacks Qwen3_5 support, which is why Phase 0 used a locally built image instead).
Example
local/qwen38-vllm-dflash2:66e5414c6d75 — the default, and the only image Phase 0 tested Qwen3.5 on.

Extra args (one per line)

What it is
Additional raw vLLM command-line arguments, one per line, appended after every other flag. Flags with a field of their own (speculative/compilation config, max num seqs, max batched tokens, KV cache dtype, prefix caching, async scheduling, mamba cache mode) are moved into that field on save, in any spelling.
Why it matters
An escape hatch for flags this editor doesn't have a dedicated field for, without needing a code change. Owned flags are lifted because a raw copy would silently override the field (vLLM keeps the last one).
Example
--disable-log-requests would suppress vLLM's own per-request access log line, on top of the flags this editor already sets.
Flags that have their own field above (speculative and compilation config, max num seqs, max batched tokens, KV cache dtype, prefix caching, async scheduling, mamba cache mode, and the tensor parallel size when GPUs are ticked) are moved into that field when you save, so each is passed to vLLM exactly once.

Auto-start on boot

What it is
Start this model automatically when the controller process boots.
Why it matters
Without it, a model stays Stopped after a controller restart until someone starts it (or a request arrives, if the model starts on request) — useful to avoid keeping every model resident by default.
Example
Enabled for the model your tools use all day, so it's ready right after the controller comes up.

On demand

Start the model when a request names it, and stop it when it is idle or another model needs its memory. All three are off unless you set them, and none needs a restart.

Start on request

What it is
Start this model when a request names it while it is stopped. The request waits until the model is Ready, then gets its answer.
Why it matters
A node that holds one model at a time can then serve several: the client names the model and the router starts it. The wait is the model's start time, up to the startup timeout (10 minutes unless configured). llama.cpp and MLX suit this. vLLM, SGLang and NIM take 2–5 minutes to start, so a client that waits for one of them may time out before it answers. The AutoStartOnRequest setting turns this on for every model; this switch turns it on for one.
Example
A coding client asks for a stopped llama.cpp model on a 16 GB card: the router starts it and answers once it is Ready. With the switch off the client gets 503 model_not_ready.
Swapping suits llama.cpp and MLX. vLLM, SGLang and NIM take 2–5 minutes to start, so a client that waits for one of them may time out before it answers.

Stop after idle (minutes)

What it is
Stop this model after this many minutes without a request. Blank means it is never stopped for being idle.
Why it matters
A stopped model gives its memory back to the node. The count starts at the model's last request, or at the moment it became Ready if it has had none. A model is not stopped while a request is in flight, or while a benchmark or tuning job runs on its node. An idle stop counts as a stop: the model does not come back after a node or controller restart. It starts again when a request names it, if it starts on request, and at controller boot if it is set to start then.
Example
15, on a model that starts on request: it leaves memory after a quiet quarter of an hour and the next request starts it again, waiting for the load.

May be stopped to make room

What it is
Allow MirbadLLM to stop this model when another model on the same node needs its memory to start on request.
Why it matters
When the memory check refuses a start on request, the router stops idle models that carry this switch, least recently used first and only as many as the missing memory needs, then tries the start once more. A model with a request in flight is never stopped, and on a node with discrete GPUs only models on the GPU that is short are considered. If the start still does not fit, the request gets the usual 503 and nothing else is stopped.
Example
Two llama.cpp models are placed on one 16 GB card that holds one of them. Both start on request and have this switch on. A request for the stopped one stops the idle one and starts the other.
